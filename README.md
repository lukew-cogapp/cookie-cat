# Cookie Cat

### [▶ Play it in your browser](https://lukew-cogapp.github.io/cookie-cat/)

A Godot 4.7 survivors-like built with Aubrey. You are a cat. Bugs come at you
from every side, your toys fight for you, and you have ten minutes to survive
the garden.

No download, no install: it runs in a browser, on a laptop or a tablet. Move
with the stick, the D-pad, WASD or a finger. Nothing else to press.

## The loop

Every toy aims and fires itself. Moving is the only control, which is what
makes the game playable one-handed by someone who cannot yet read.

Bugs drop gems, gems fill the bar across the top, a full bar stops the game and
offers three cards. Pick a new toy or make one you have stronger. Repeat until
the clock runs out.

- **Ten minutes.** Surviving to the end is a win and pays a cookie bonus.
- **Five hearts.** Being touched costs one, then the cat flashes for a second
  and a half and shoves every bug clear, so being surrounded is survivable.
- **Nothing dies badly.** Bugs pop into sparkles, and a run that ends early
  still ends on a tally rather than a failure.

## Cats

Five, all free. Each opens with a different toy, which is the whole difference
between them: a starting weapon changes how a run has to be played from the
first second, where a stat bonus is a number a child cannot see. Picking one is
the first decision of a run, not a reward to grind for.

| Cat | Opens with |
| --- | --- |
| Cookie Cat | Paw Swipe |
| Minty | Yarn Ball |
| Berry | Fish Friends |
| Choccy | Purr Ring |
| Lion | Static Fur |

Cookies are earned by playing and spent on cosmetics, which change nothing
about how a run goes.

## Toys and helpers

Ten toys, each a different shape of attack rather than a different number: a
swipe all round the cat, a thrown ball, a standing aura, orbiting fish, a
chaser, a puddle on the ground, a bolt across the screen, a big slow burst, a
feather wand that flies out and comes back, and a trail of crumbs dropped as
you run. Six helpers multiply what the toys already do. All of it is listed
with its numbers in `scripts/tuning.gd`, the only file that holds any.

## Layout

```
project.godot            input map, autoloads, main scene
scripts/tuning.gd        every tunable number, autoloaded as `Tuning`
scripts/save_state.gd    cookies and what they have bought, autoloaded as `Save`
scripts/run_state.gd     one run's clock, xp and picks, autoloaded as `Run`
scripts/swarm.gd         every enemy, as rows in arrays and one MultiMesh
scripts/weapons.gd       every toy, fired on its own cooldown
scripts/gems.gd          xp, hearts and cookies, same array pattern
scripts/director.gd      what spawns when, from the wave table
scripts/ground.gd        scattered ground decals
scripts/props.gd         breakable pots, bushes and boxes
scripts/puffs.gd         pooled burst particles and floating numbers
scripts/*.gd             behaviour only, no literals
scripts/tools/make_art.py  draws every sprite from pixel grids
assets/*.png             16x16 sprites, all generated by the tool above
ui/*.tres                shared panel and card styles
addons/gut/              vendored test framework, do not restyle
test/*_test.gd           GUT suites; run them with test/run.sh
test/shots.gd            windowed screenshot renderer
```

Two conventions worth keeping:

- **Numbers live in `tuning.gd`.** Playtesting means editing one file, and
  GDScript hot-reloads, so values can change while the game runs.
- **Art is generated.** `scripts/tools/make_art.py` holds a pixel grid per
  sprite, so a new bug is a grid there rather than a file to find and license.
  Rerun it after editing a grid.

## Enemies are not nodes

The one architectural decision worth knowing before reading the code: an enemy
is a row in parallel arrays in `swarm.gd`, moved in one loop and drawn by one
`MultiMesh` per kind. Nothing about a bug needs a node, a script instance or a
physics body, because bugs collide with nothing but the cat, and that is a
distance check. The same design holds several hundred. Gems, shots, puddles,
props, ground decals and particles all follow the same pattern.

Rows are swap-removed, so a kill moves the last row into the dead one's index.
`test/swarm_test.gd` pins the ways that can go wrong.

## Running it

```
godot --path .                                        play
godot --headless --path . --import                    after a fresh clone
godot --headless --path . -s test/compile_check.gd    compile everything
./test/run.sh                                         the test suites
./test/run.sh swarm_test.gd                            one suite
godot --path . -s test/shots.gd                        screenshots
python3 scripts/tools/make_art.py                      redraw the sprites
```

A fresh clone needs the import once: GUT's `class_name` registrations live in
`.godot/`, which is gitignored, and without them the suites refuse to run.

`test/shots.gd` must run **windowed**. Under `--headless` the dummy renderer
writes blank images, and looking at the pictures is the only way to catch the
things numbers miss: a cat smaller than the bugs, a snail rendering as a white
bar, a lawn that reads as graph paper. All three shipped past green tests.

Only one Godot process at a time per checkout. Concurrent runs fight over
`.godot/` and hang with no output at all.

## Deploying

Tagging publishes to GitHub Pages:

```
git tag v1 && git push --tags
```

Tags rather than every push, so a half-finished build never replaces the one
people have the link to.
